# VARYN 17S-18 | Parent-approved read-only synthetic fixture to real AppContainer IPC

Date: 2026-11-05. **State: CI-ONLY experimental boundary. No real human consent or private-file capability.** PR #1 remains OPEN/DRAFT against unchanged main.

## Why this milestone matters

17S-17 proved the trust infrastructure with an actual zero-capability Windows AppContainer: attested primary token and approved inherited pipe identities BEFORE resume, excluded known decoy event by native trusted-parent object comparison, attached a 192 MiB / one-process / kill-on-close Job Object, validated one bounded round-trip and confirmed a running child is killed when its Job closes.

Until 17S-18, the trusted parent still hardcoded \`[4,6,11]\` as its request. There was **no distinct parent-owned resource authorization boundary** that accepted a specific host read-only source after an approval decision. This milestone introduces only that *synthetic* bridge.

## Implementation

- \`varyn/parent_synthetic_read_broker.py\` defines \`ParentSyntheticReadBroker\`, strictly gated by hosted CI plus \`VARYN_CI_APPCONTAINER_TRIAL=1\`. It permits only **one fixed filename**, \`synthetic-parent-counts.json\`, inside a trusted disposable test root. The caller cannot supply a model-chosen path, arbitrary extension, URL, command, mutation, provider token or general-file grant. File source limit is 512 bytes; count lists contain 1–12 strict integers 0–10,000. Duplicate JSON keys, invalid encoding, nonfinite values, extra fields, symlinks and oversized/nonregular files fail closed.
- The parent obtains **metadata only** before approval. It creates a one-use \`SyntheticReadPreview\` bound to a random 128-bit request ID, random nonce, exact synthetic filename, file identity (device/inode/size/mtime) and 20-second expiry. The preview contains no source text, credentials or sensitive data. \`owner_decide(request_id, displayed_digest, approved=bool)\` is intended exclusively for a **trusted host-side UI callback**, not untrusted model or child text. This milestone invokes it with \`approved=True\` **only from CI test code**, hence the approval is **simulated**, not the user's actual click.
- After approval, \`claim_and_prepare()\` *burns* the approval, revalidates the file's identity, opens and parses only the approved synthetic fixture, validates exact schema, and commits a hash-only request ID in the parent-owned SQLite \`DurableOneShotJournal\` **BEFORE child creation/dispatch**. It produces only a bounded \`{version,action,request_id,nonce,counts}\` envelope. The child never receives the approved source filename, its host path, opened handle, grant token, or any permission to select another file. The child does receive a **different known-existing synthetic host-file path** solely as the preexisting negative Windows file-denial test; this is not the newly approved source.
- The real Windows \`run_ci_only_zero_capability_trial(parent_read_trial=True)\` creates a fresh disposable parent-side fixture and AppContainer profile, simulates the trusted host decision, claims the dispatch, starts a real suspended child with \`SECURITY_CAPABILITIES\` and an exact two-anonymous-pipe \`HANDLE_LIST\`, attests the actual primary token, **independently checks two expected pipe kernel objects and the excluded known event** before resume, and attaches a verified one-process, 192 MiB, kill-on-close Job Object. Only then does the child receive the bounded counts. The existing child still requires a granted synthetic read and refusal of the known-present host-owned synthetic file, and returns a nonce/request-ID-correlated sum of 21.
- The parent independently validates the response against the approved source's expected sum, **not** a model assertion. Only then is the previously claimed SQLite request marked \`completed\`. Any invalid response makes that request \`failed\` or leaves it \`claimed\` on a crash; either state blocks automatic reuse of the same request ID. Revocation before dispatch rejects the read; revocation after dispatch cannot undo what already ran and rejects further acceptance.

## Adversarial test gates

\`tests/test_parent_synthetic_read_broker.py\` exercises: denied/missing approval, nonboolean decisions, forged preview digest and request ID, duplicate preview, no content read before consent simulation, scoped read-only request, expiry before decision and before dispatch, fixture change after preview, symlink rejection, invalid file shapes/byte bounds/boolean payloads, forged nonce/total and extra/truncated replies, response replay, revocation before/after dispatch, corrupted response finalization and **cross-restart SQLite claim/no-replay**.

\`tests/test_windows_appcontainer_trial.py::test_parent_approved_readonly_fixture_reaches_real_appcontainer\` is a **hard native Windows gate** requiring actual AppContainer token attestation, no extra capability SIDs, exact two pipe handles and known excluded decoy, pre-resume Job membership, simulation-bound parent approval and file read, absence of approved host source path in child request, an actual bounded nonce-correlated IPC response, denied separate synthetic host-file read, a completed parent journal claim and deleted profile. It does not run native code on the owner's Windows laptop.

\`.github/workflows/memory-checks.yml\` adds a dedicated 17S-18 portable adversarial gate and names the early Windows native AppContainer gate accordingly. Ubuntu validates portable semantics, but cannot attest Windows kernel behavior.

**Source-side milestones verified before the final documentation commit:** previous 17S-17 final [Actions #41973204163](https://github.com/naraya07pedro-spec/VARYN/actions/runs/41973204163), Windows/Ubuntu COMPLETED SUCCESS, 17S-17 full Job and handle tests passed. The isolated parent-broker portable tests passed on [Actions #41973989562](https://github.com/naraya07pedro-spec/VARYN/actions/runs/41973989562). ## What this does NOT do

1. **No actual human permission was collected.** A trusted CI driver simulated approval; the desktop GUI has NOT yet wired the new preview/decision pair to the user.
2. No live filesystem bridge exists for normal user data. The test root and fixed basename are disposable CI-generated fixtures. General Windows reparse-point, symlink-race, path-root hardening and directory handle pinning have not been audited for real documents.
3. No general tool API, real read-only owner document, web/CRM/provider credential, mutating operation or arbitrary filename is accessible from the child. No production \`ProcessRepoFetcher\` integration occurred. Its \`os_sandbox=False\` and \`windows_restricted_primary_production_enabled=False\` continue to be correct.
4. The in-memory approval object is not restart-persistent. The SQLite claim is durable *while its DB is retained*, but in this test the entire journal is removed with its temporary directory after verification. This does not constitute production-grade consent history.
5. No cross-thread/process handle-inheritance serialization has been proven. The 17S-17 Job limit readback and kill-on-close checks are real, but deliberate OOM, second-process spawning and network egress penetration tests remain undone. The pre-resume audit checks three known fixture handles, **not every handle**.
6. Model/child output is untrusted, even when it comes from an attested AppContainer. The expected sum is a synthetic deterministic oracle, not proof that arbitrary real tool results are correct.
7. **Option C is still unmet:** the user demands automatic bidirectional conversation/history/memory synchronization with the **official consumer ChatGPT, Claude and Gemini apps**, not an API-only replacement or a custom chat shell. None of that external integration was implemented in 17S-18.

## Recommended next product gate

Shift emphasis toward a **useful owner-facing, read-only workflow** instead of building more isolated synthetics indefinitely. The next defensible test is to bind the existing desktop approval preview/digest UX to a one-time parent broker grant for a narrowly chosen non-sensitive local source, with an explicit opt-out, revocation and real owner-device acceptance. Only after that is demonstrated should a real file type be exposed via a production broker, followed by hard adversarial OS and data-integrity tests. Keep the present AppContainer code test-only and never auto-import real user files.
