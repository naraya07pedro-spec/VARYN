# VARYN 17S-14 | Real AppContainer one-shot synthetic broker transport

Date: 2026-11-05. **Status: hosted Windows OFFLINE synthetic transport verified. NOT a production broker or general sandbox.** PR #1 stays DRAFT, \`main\` unchanged. User's Option C official consumer-app history synchronization remains unfulfilled.

## Objective and scope

Move past 17S-13's fixed single-purpose exit-marker proof: demonstrate that a trusted host can deliver one *bounded and authenticated* request to a real Windows AppContainer Python child, receive and verify one result, reject reuse and malicious input, and still attest that the child cannot read a known-present synthetic host-only file.

The proof operates **only on ephemeral GitHub Actions Windows runners** and performs no network request, private-file read, GitHub write, external AI request or shell operation. The fixed action is \`sum_synthetic_counts\` applied to a 1–12-element list of integers from 0 to 10,000. It is not an AI agent, not a general-purpose tools endpoint and not an automation capability.

## Changes delivered

- \`varyn/bounded_broker_protocol.py\`: portable JSON envelope with strict duplicate-key rejection and 2,048-byte maximum; exact schema/version and action allowlist; 32-byte ephemeral HMAC-SHA-256 key; 128-bit fresh request ID and nonce; 20-second issued-at window; exact payload/value types; signed response with matching request ID and nonce; bounded integer result; and a one-use reply verifier. On ANY validation attempt, the verifier is consumed so a forged response cannot be followed by automatic acceptance/retry. Unsupported tool actions are default-denied. **One-use response consumption is local to the verifier instance; it is not durable cross-restart replay prevention.**
- \`varyn/bounded_broker_child.py\`: fixed \`-I -S\` Python script with one operation and no loop. It first reads and verifies a granted synthetic AppContainer file, next requires \`PermissionError\` on a separately created known-existing owner-only synthetic file, and then handles the one signed request via \`offline_child_once\`. Missing private file, unexpectedly permitted host-file read, malformed request, or response write error returns a distinct failure code; success marker is \`73\`.
- \`varyn/windows_appcontainer_trial.py\`: opt-in \`broker_trial=True\` path restricted to hosted Windows CI. It creates a **new disposable AppContainer profile**; copies only trusted Python runtime and standard library (excluding \`site-packages\`, site-user files and unnecessary large libraries), plus fixed protocol/child modules, into the OS-supplied profile directory. Host writes one exclusive-create request and random ephemeral key file. \`CreateProcessW\` starts the actual child SUSPENDED with zero AppContainer capabilities and no inherited handles; the host verifies the actual child primary token and SID before resume. Once complete, the host reads a **bounded** response, verifies MAC and nonce/request correlation, ensures \`21\` is the expected result of the fixed synthetic \`[4,6,11]\` input, then tests that repeating response consumption is rejected. One process, one request, one response. All runtime copies and profile are deleted.
- \`tests/test_bounded_broker_protocol.py\`: portable tamper, HMAC mismatch, forged result, stale/future timestamp, duplicate JSON key, oversized request, schema/action/quantity invalidity, mismatched request identity, exclusive response creation, and replay denial tests.
- \`tests/test_windows_appcontainer_trial.py\`: actual hosted Windows AppContainer proof of one signed request and verified response **in addition** to the existing granted-file and denied-host-file controls. The normal owner PC and Linux cannot create an AppContainer profile through this trial.
- \`.github/workflows/memory-checks.yml\`: dedicated 17S-14 portable protocol regression step; existing 17S-13 native test module now includes the 17S-14 actual AppContainer test. The tests are run on Windows and Ubuntu, but ONLY hosted Windows can attest native AppContainer operation.

## Threat model and limitations, explicitly NOT solved

1. The protocol is file-mediated inside a shared profile-owned directory. The **child itself can read the ephemeral HMAC key file**: this authenticates/links a response for the CI exchange and resists accidental/unauthorized modifications by actors without the key, but **does not stop a compromised child or a same-user attacker who accesses the key from signing forged data**. This is **NOT a cryptographically trusted response from arbitrary malicious code**. Production authentication should use broker-held keys or OS-bound authenticated IPC and verify the caller's OS identity, not secrets readable to an untrusted worker.
2. The current replay defense consumes one verifier and uses exclusive-create response files in one ephemeral test profile. It does not implement a durable global replay journal, crash recovery, or multiple requests across process restarts. Do not present it as complete replay protection.
3. **No end-user consent or unattended task permission was added.** There is no production request routing, cancellation in a real GUI, user-specific policy, full tool result validation, audit trail for production actions, or automatic replay.
4. Real network egress absence was not independently tested, even though no network-capability SIDs are granted and the code performs no network requests. No comprehensive OS escape, COM/IPC, privileged-handle, LPAC, filesystem or package ACL audit has been performed.
5. Test-only Python runtime copy includes standard library dependencies and is NOT an immutable signed runtime image supply-chain boundary. CI-runner validation is not acceptance on the owner's Windows computer.
6. The production \`ProcessRepoFetcher.status()['os_sandbox']\` remains \`False\`, and \`['windows_restricted_primary_production_enabled']\` remains \`False\`; **private files, mutating tools, agent autonomy, broad GitHub access and provider sync stay disabled.**
7. **Option C** remains automatic, bidirectional conversation/history and memory synchronization across **official consumer ChatGPT, Claude and Gemini applications**, not API-only proxying or a custom replacement UI. A secure local AppContainer broker does not satisfy this externally blocked requirement.

## Verdict and 17S-15 next gate

**17S-14 is a successfully demonstrated offline, one-shot AppContainer communication primitive with real process token verification and synthetic host-file denial.** It is not a production broker.

The next improvement should be an OS-identity-bound, broker-held-authentication channel (e.g., narrowly scoped Windows named pipe with explicit ACL, caller PID/token verification, no key readable by child), plus a durable no-replay dispatch journal, Job Object / cancellation / memory and time limits, fail-closed malformed input checks and independent owner's-device acceptance. No private or mutating data access until those specific gates pass.
